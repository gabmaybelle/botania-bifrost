# Botania Bifrost: porting Botania to Minecraft 26.3 (Fabric + NeoForge)

Botania Bifrost is an unofficial port of Botania by Vazkii and the Botania contributors. Public on GitHub, built from the official `1.21.1-porting` branch.

This file is the working plan and log. Claude Code should read it at the start of every session and update the log at the end.

## Decisions

- **Name:** Botania Bifrost. Repository and Modrinth slug: `botania-bifrost`. Summary line: "An unofficial port of Botania to 26.3 for Fabric and NeoForge."
- **Mod ID:** keep `botania`, so worlds and addons can move to an official 26.x release later. Display name is "Botania Bifrost"; jars are named `botania-bifrost-<loader>-<mc version>-<build>.jar`.
- **Version jump:** go straight from 1.21.1 to 26.3, reading the porting notes for every release in between, in order, from 1.21.2 through 26.3. NeoForge publishes porting primers for each version; Fabric publishes update blog posts.
- **Upstream:** keep `upstream` as a git remote and cherry-pick fixes from `1.21.1-porting`.
- **Style:** keep upstream's code style (`spotlessJavaApply`) so upstream fixes still apply cleanly.

## Phases

Each phase ends with both loaders building and the relevant GameTests passing on both.

### Phase 0: Baseline
1. Fork upstream on GitHub as `botania-bifrost`, create branch `26.3` from `1.21.1-porting`.
2. Build both loaders on Java 21 with no changes. Run the GameTests. Record results below.
3. Add the unofficial notice to the README.

**Done when:** the untouched 1.21.1 branch builds and its test results are recorded.

### Phase 1: Toolchain and compiling
1. Update `gradle.properties` and `gradle/libs.versions.toml` to the target toolchain, Java 25. Set the display name to Botania Bifrost and the jar names as above; leave the mod ID as `botania`.
2. Disable optional integrations and Patchouli, Trinkets and Curios behind clear `// PORT-26.3: disabled` comments.
3. Fix `Xplat` until it compiles, then `Fabric`, then `NeoForge`.
4. Rerun datagen.

**Done when:** both jars build, the game reaches the main menu on both loaders, and a new world loads.

### Phase 2: Core mana loop
Pure Daisy, livingwood and livingrock, mana spreaders and bursts, mana pools, sparks, mana infusion, Petal Apothecary, generating flowers.

**Done when:** related GameTests pass on both loaders and a pool fills from an Endoflame in-game.

### Phase 3: Functional flowers
Start with the farm and mob flowers (Agricarnation, Hopperhock, Rannuncarpus, Pollidisiac, Bellethorne, Dreadthorne and similar), then the rest.

### Phase 4: Items, tools and rendering
Manasteel, Terrasteel, Elementium gear, rods, Runic Altar, Terra Plate, particles and custom rendering. Audit every mixin against 26.3.

### Phase 5: Accessories, Lexica and recipe viewers
Trinkets Updated on Fabric, Curios on NeoForge, Patchouli, and whichever recipe viewers exist for 26.3.

### Phase 6: Endgame and polish
Alfheim portal, elven trades, Gaia Guardian, Corporea, Garden of Glass. First public release.

## API changes (vazkii.botania.api)

The API package is kept verbatim except where 26.3 forces a change. So far, all of it is renames the
whole codebase got: `ResourceLocation` -> `Identifier` (55 API files), `ResourceKey#location()` ->
`identifier()`, `InteractionResultHolder`/`ItemInteractionResult` -> `InteractionResult`,
`BlockPos#getCenter()` -> `Vec3.atCenterOf(pos)`. Tools and armour (step 3): `getManasteelItemTier()`, `getElementiumItemTier()` and `getTerrasteelItemTier()` return `ToolMaterial` (vanilla removed `Tier`), and the four `get...ArmorMaterial()` getters return `ArmorMaterial` instead of `Holder<ArmorMaterial>` (armor materials are no longer a registry). Recipes (step 3): vanilla's `Recipe` changed shape in 1.21.2, so the Botania recipe interfaces follow it. New in the API: `BotaniaRecipe<T>` (all Botania recipe interfaces extend it) with vanilla's new required methods as defaults: `placementInfo()` = not placeable, `recipeBookCategory()` = one Botania category (`botania:botania`, registered by the mod), `group()` empty, `showNotification()` false. Changed: `assemble(input, registries)` -> `assemble(input)` and `ElvenTradeRecipe#tryAssemble(input, registries)` -> `tryAssemble(input)` (vanilla's assemble lost the registries); `getType()` returns the precise `RecipeType<? extends X>`; `canCraftInDimensions` defaults removed (vanilla removed the method). Kept as Botania's own methods, no longer overrides of vanilla: `getIngredients()` (declared on each processing recipe interface), `getResultItem(registries)`, `getRemainingItems(input)` (`RecipeWithCatalysts`, brewery), `getToastSymbol()`. Consequence for later: the server no longer sends machine recipes to clients, so the Lexica pages, recipe viewers and the Assembly Halo's client preview need Botania to sync its own recipes (Phase 5); `PatchouliUtils#getRecipeGroup` is a placeholder until then. Blocks and entities (step 3): `SpecialFlowerBlockEntity`, `FunctionalFlowerBlockEntity`, `GeneratingFlowerBlockEntity` and `BindableSpecialFlowerBlockEntity` save and load through vanilla's new `saveAdditional(ValueOutput)` / `loadAdditional(ValueInput)` (addon flowers that override the old `CompoundTag` pair must follow; the packet-side `writePacketNBT`/`readPacketNBT` and `getUpdateTag` still use `CompoundTag`). `MobSpawnData` no longer carries its weight: `MobSpawnData.Builder#build()` returns `Weighted<MobSpawnData>`, the `spawnedMobs(...)` builders take `Weighted<MobSpawnData>...`, and `GaiaFightConfiguration`/`LooniumStructureConfiguration` hold a `WeightedList<MobSpawnData>` (the JSON format is unchanged: `weight` is still written inline). `LifeAggregatorCarryable`'s default `getCarriedData` builds the block entity tag through a `TagValueOutput`. `FloatingFlower`, `CorporeaRequestMatcher` and the corporea deserializers keep their `CompoundTag` signatures (bridged in `NbtHelper`).

API changes in pass 5: `WandHUD#renderHUD`, `MonocleHud#renderHUD` and `BotaniaAPIClient#drawSimpleManaHUD`/`drawComplexManaHUD` take a `GuiGraphicsExtractor` instead of a `GuiGraphics` (the class is gone); `BindableSpecialFlowerBlockEntity.BindableFlowerWandHud` follows.

API changes in pass 7 (loader-facing, not `vazkii.botania.api`): `BotaniaItemProperties#init` is replaced by `registerTests`/`registerRanges`; `ColorHandler#submitItems` by `submitItemTintSources`, and `submitBlocks` hands out `BlockTintSource`s; `BotaniaSpecialModelRenderers#register` is new. Loaders: NeoForge has `RegisterConditionalItemModelPropertyEvent`, `RegisterRangeSelectItemModelPropertyEvent`, `RegisterSpecialModelRendererEvent`, `RegisterColorHandlersEvent.Block`/`.ItemTintSources`; the Fabric API jars in hand show no registry for these, so check the current Fabric API (or the vanilla id mappers) when the Fabric project is ported.

API changes in the leftovers pass (not `vazkii.botania.api`): `BotaniaFeatures#registerFeatures` takes `BiConsumer<MapCodec<? extends Feature>, Identifier>` (feature types are codecs in `BuiltInRegistries.FEATURE_TYPE`); `MysticalFlowerFeature` is a record of its own settings and `MysticalFlowerConfig` is gone, so the configured feature JSON lists `tall_chance` and `to_place` next to `type` (data/datagen, step 4); `BlockWithTooltip` + `TooltipBlockItem` replace the vanished `Block#appendHoverText` for the platforms, flower motifs and mana pools.

API changes in the loader passes: `TinyPotatoRenderCallback#onRender` (`vazkii.botania.api.fabric.item`, the Fabric event behind `ClientXplatAbstractions#fireRenderTinyPotato`) takes a `SubmitNodeCollector` instead of a `MultiBufferSource`, which 26.3 removed. Loader-facing (not `vazkii.botania.api`): `XplatAbstractions#getSmeltingBurnTime` takes the `Level` as well as the stack, because a fuel value can be a data-driven provider that needs a loot context to resolve; `LootHandler#injectLoot`/`injectGogLoot` (Fabric) take the registries the loot event hands over, because nested loot tables are referenced by holder now.

API change for the lint (no behaviour change): `RunicAltarRecipe#getIngredients` carries `@Override`, as it redeclares an inherited method and PMD's `MissingOverride` fails the build otherwise.

API changes in the NeoForge client pass: `TinyPotatoRenderEvent` (`vazkii.botania.api.neoforge.item`) carries a `SubmitNodeCollector collector` instead of a `MultiBufferSource buffers`, the NeoForge twin of the Fabric callback change above.

## Rendering (Phase 1, step 3)

Minecraft rewrote its rendering between 1.21.9 and 26.3. A renderer no longer draws into buffers: it copies what
it needs into a *render state* on the game thread, then *submits* drawing requests (a model, an item, a block, a
custom shape) to a `SubmitNodeCollector`, and the game draws them later in sorted batches. The mapping Botania
follows, pass by pass:

| Was (1.21.1) | Is (26.3) | Botania |
|---|---|---|
| `ShaderInstance` + shader JSON, `RenderType.CompositeState` and `RenderStateShard`s, `RenderTypeAccessor#create` | `RenderPipeline` (GLSL files, vertex format, uniform blocks, blend and depth state, declared in code) + `RenderSetup` (textures, lightmap, overlay, sorting) + `RenderType.create` | `CoreShaders` holds the pipelines, `RenderHelper` the render types. The nine GLSL shaders are rewritten to the `#version 330` include style (`GameTime` comes from the `Globals` block). Values the old code set as uniforms each frame (Gaia grain and disfiguration, boss bar health) ride on the vertex colour now, see the pipeline comments. The "use shaders" option is read when the types are created: it takes effect after a restart. The old `.json` shader files are gone. |
| `RenderType.lines()` with a `LineStateShard` width | one `LINES` pipeline, width per vertex (`setLineWidth`) | the four `LINE_*_NO_DEPTH` types are one type; `RenderHelper#line` adds a line with its width |
| `ItemBlockRenderTypes#setRenderLayer`, `BlockRenderLayers` | layers are read off the textures (26.1) | `BlockRenderLayers` deleted |
| `MultiBufferSource`, `BufferBuilder`/`Tesselator` draws, `RenderSystem#setShader*` | `SubmitNodeCollector#submitCustomGeometry` and friends | world helpers take the collector |
| `GuiGraphics` with `blit`/`fill`/`drawString`/`renderItem` | `GuiGraphicsExtractor` with `blit(pipeline, ...)`/`fill`/`text`/`item`; custom shapes are `GuiElementRenderState`s added through `GuiGraphicsExtractorAccessor` | HUD helpers in `RenderHelper`; the progress pie is a custom element; a GUI item cannot be faded any more (`renderGuiItemAlpha` draws it fully) |
| `ItemRenderer`, `BakedModel`, `BlockRenderDispatcher` | `ItemModelResolver` + `ItemStackRenderState#submit`, `BlockModelResolver` + `BlockModelRenderState#submit`; quads come with their own `RenderType` (`BakedQuad.MaterialInfo`) | `renderItemCustomColor` resolves the item and submits its quads with the colour forced through a `QuadInstance` (accessor mixins read the resolved layers) |
| `BlockEntityRenderer#render(T, partialTick, pose, buffers, light, overlay)` | `createRenderState()`, `extractRenderState(T, S, partialTick, cameraPos, crumbling)`, `submit(S, pose, collector, camera)` | `BotaniaBlockEntityRenderer` keeps the one `render` method (the block entity is null for the item form, the camera is null there too) and drives it from the two vanilla steps; `BotaniaBlockEntityRenderState` carries the block entity and partial tick for now. Hand-drawn shapes go through `RenderHelper#submit` (custom geometry with a fresh `PoseStack`), items through `submitItem`, block models through `submitBlockState`/`submitBlockModel`, entities through `submitEntity`, text through `SubmitNodeCollector#submitText`. Models are `Model<Unit>` with the root in the constructor; `renderToBuffer` is final, so the Teru Teru Bozu picks its face with `setRaining` and the Gaia head renderer picks the skull model itself (`GaiaHeadModel` draws nothing). |
| `EntityRenderer#render`, `RenderLayer#render`, `Model#renderToBuffer`, `HumanoidModel<T>` | `submit(...)` with entity render states, `Model<S>` generics, `RenderLayer<S, M>` | Each Botania entity renderer has a small render state next to it (`SparkRenderState`, `GaiaGuardianRenderState`, ...) filled in `extractRenderState` and drawn in `submit`. The Gaia Guardian's grain and disfiguration ride on the model tint (`getModelTint`); the pixie picks its noise layer in the renderer (`getRenderType`) instead of a static flag in the model. The player layers (`ContributorFancinessHandler`, `ManaTabletRenderHandler`, `TerrasteelHelmetLayer`) are `RenderLayer<AvatarRenderState, PlayerModel>`; the first two look the player up by `state.id` because the state has no name or inventory. `ArmorModel` reads armour stand poses from `ArmorStandRenderState` and applies the slot's part visibility in `setupAnim`. `AccessoryRenderer#doRender` takes a `SubmitNodeCollector`; the bauble renderers draw their gem models with `RenderHelper#submitBlockModel` (the tiara wings lose the item glint and the blood pendant gem takes the brew colour directly, as item colour handlers are gone). `ModelPart#copyFrom` is `loadPose(other.storePose())`. |
| `TextureSheetParticle`, `ParticleRenderType` with begin/end | `SingleQuadParticle` with a `Layer` (atlas + pipeline); `ParticleRenderType` is now the engine group (`SINGLE_QUADS`, `ITEM_PICKUP`, ...) | Wisps and sparkles are `SingleQuadParticle`s on `CoreShaders.ADDITIVE_PARTICLE` (depth-ignoring wisps: `ADDITIVE_PARTICLE_NO_DEPTH`, corrupt sparkles: `FILM_GRAIN_PARTICLE`), marked solid so the engine never wants an order-independent-transparency pipeline for them. The particle atlas keeps its own sampler, so the bilinear filtering the old code switched on around them is gone (`setFilterSave`/`restoreLastFilter` removed from `ClientXplatAbstractions`; the Fabric `ExtendedTexture` mixin goes with the loader pass). `FlowerItemPickupParticle` extends vanilla's `ItemPickupParticle` (the engine's item pickup group draws the extracted item render state) and only swaps the target for the block centre. `BoltRenderer` draws through `RenderHelper#submit`. |
| `HudRenderCallback`, `RenderGuiLayerEvent` | `HudElementRegistry` (Fabric), `RegisterGuiLayersEvent` (NeoForge); screens on the extractor | Every HUD and screen takes a `GuiGraphicsExtractor` (`text`, `item`, `fakeItem`, `itemDecorations`, `centeredText`, `blit(pipeline, ...)`). Its pose is a 2D `Matrix3x2fStack`, so z offsets are gone (later draws land on top). `RenderSystem` blend, depth and shader-colour calls are gone; where the colour carried a tint or alpha, `RenderHelper#drawTexturedModalRect` takes an ARGB colour. The Gaia boss bar draws through the `GAIA_BOSS_BAR` pipeline with grain in red and health in alpha. Container screens set their image size through the constructor and override `extractBackground`/`extractLabels`; tooltips are vanilla's job. The mana bar tooltip implements `extractText`/`extractImage`. Keys: `KeyMapping#matches(KeyEvent)`, modifiers on the event, `InputConstants.KEY_*` (not GLFW codes); the current screen is `minecraft.gui.screen()`; `Profiler.get()`; `minecraft.gui.hud.isHidden()`. The sextant's radius circle is a ring of small fills (no line strips in the GUI). |

### Recipes on the client

Vanilla 26.3 keeps recipes on the server (`Level#getRecipeManager` is gone; the client gets the recipe book, the
stonecutter list and the recipe property sets). Botania reads recipes on the client in several places: the mana pool
and petal apothecary HUDs, the runic altar's client tick, the terra plate's input check, the Orechid wand HUD, the
assembly halo (crafting recipes by id) and the rod of the molten core (smelting, both sides), plus the lexicon pages.
So each loader sends the client a copy of `BotaniaRecipeTypes.SYNCED_TYPES` (Botania's ten types plus `CRAFTING` and
`SMELTING`) on join and after a reload (NeoForge: its own datapack sync event; Fabric: `UpdateRecipesPacket`), stored in
`SyncedRecipes`. `BotaniaRecipeTypes#getAllRecipesFor(Level, type)`, `getRecipeFor(Level, type, input)` and
`byKey(Level, key)` answer from that copy for client levels and from the server's manager otherwise; `recipeManager(Level)`
stays server-only for the crafty crate and the halo's crafting. The sync surfaced a latent bug from the recipe pass: the
16 stateless special crafting recipes decoded as fresh instances but used `StreamCodec.unit(new X())`, which refuses to
encode any other instance; they now share one `INSTANCE` for both codecs, as vanilla's `RepairItemRecipe` does.
The `OrechidManager` caches are kept per side, like `BotaniaRecipeIngredientsCache`: the server reload listener clears
the server's, and `SyncedRecipes` clears the client's whenever a new copy arrives. Upstream shared one set, so a client
on a dedicated server kept stale Orechid weights after `/reload`, and in singleplayer both threads used the same maps.

### Game tests

Since 1.21.5 a game test is two registry entries: a test function (code, built-in registry `TEST_FUNCTION`) and a test
instance (structure, timeout, environment; the data-driven `TEST_INSTANCE` registry). Tests are batched by environment.
Fabric's `fabric-gametest` entrypoint now only finds Fabric's own `@GameTest`, and has no generators or batch hooks.
`vazkii.botania.test.BotaniaGameTests` keeps the list of test classes (it was the entrypoint list in `fabric.mod.json`)
and turns their `@BotaniaGameTest`, `@BotaniaGameTestGenerator`, `@BotaniaBeforeBatch` and `@BotaniaAfterBatch` methods
into those entries, the way vanilla's old scanner did (a fresh instance per call, ids `botania:<class>.<method>` in lower
case). Each batch is a `BotaniaTestEnvironment` (`botania:batch`) that runs the batch's before and after methods. On
Fabric, `FabricCommonInitializer#registerGameTests` registers the environment type and the functions, and adds the
instances through `DynamicRegistrySetupCallback`, only when `-Dfabric-api.gametest` is set (`:Fabric:runGameTest`).
On NeoForge, `NeoForgeCommonInitializer#registerGameTests` does the same through `RegisterEvent` and
`RegisterGameTestsEvent`, only when `GameTestHooks#isGametestEnabled` (`:NeoForge:runGameTestServer`). Vanilla reads
`.snbt` test scenes only from a folder on disk (`StructureUtils.testStructuresSourceDir`, `data/<ns>/structure/...`),
and Fabric's hook that reads them from mods is Fabric-only, so the NeoForge run first copies Botania's scenes into
`NeoForge/build/gametest-structures` (`copyGameTestStructures`) and points that folder at the copy
(`-Dbotania.gametest.structures`). `TestingUtil.EMPTY_STRUCTURE` is vanilla's `minecraft:empty` on both loaders.

Test positions changed meaning: 1.21.1 counted them from the structure block, one block below the structure; 26.3 counts
them from the structure's own corner (`GameTestHelper#absolutePos` uses `TestInstanceBlockEntity#getStartCorner`). So
the 32 scenes in `data/botania/gametest/structure` got an empty bottom layer (every block and entity one higher,
`size` one taller), which keeps every position in the test code as upstream wrote it.

Scenes are placed without block updates now (`TestInstanceBlockEntity#placeStructure`, flags 818), so a block whose
state depends on its neighbours keeps the state written in the scene. The scenes predate the `powered` property on
Botania's flowers and spreaders; where a lever is already on at the start, the block it powers is marked
`powered:true` in the scene (the target Dandelifeon in `dandelifeon_transfer`; the three lever-powered spreaders in
`spreader_pool_default_aim`, which otherwise sometimes fired into their pools before the test began). `RarityConsistencyTest` reads results
through recipe displays; a smithing trim recipe's display is a sample trimmed armour piece, so trim recipes are skipped,
as their empty `getResultItem` made 1.21.1 skip them. `MultiblockTest` builds the terrestrial agglomeration plate, the alfheim portal (along X and along Z) and the mana
enchanter (both axes) by hand in an empty `multiblock_arena` scene and checks that they are accepted, and rejected with
one block wrong. The test servers run without Patchouli's classes, which also shows the structure classes load
without them; `TranslationKeysTest#everyItemHasValidDescriptionId`, which crashed on them before, runs and passes.

### Mixin targets

class, every injected method (it must exist in the target class itself, with the descriptor if one is given), the

target classes that no longer exist or changed kind; and the datagen run boots the client far enough to apply the

## Datagen (Phase 1, step 4)

The generators come back in passes, the same way as the loaders: data side first (tags, loot, advancements, the
Loonium and Gaia config files, banner patterns, the recipe builders), then the recipe providers (Fabric project),
then the models and item definitions, then the two loader entry points, and only then a datagen run that is diffed
against the JSON currently in `src/generated`. What changed underneath in 26.3: recipes, loot tables and
advancements are registries now, written through `BootstrapContext`s (`RecipeProvider`, `LootTableProvider`,
`AdvancementProvider` are bootstraps, not file writers), tag appenders only take resource keys, number providers in
loot tables are registry holders, and nested loot tables are referenced by holder.
